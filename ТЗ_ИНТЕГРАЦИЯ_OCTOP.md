# ТЗ — Интеграция механик Octop (Этап-2+, блоки О1–О7)
Техническое задание · Надстройка над ТЗ.md (v3.1) и CONTRACTS.md §8–§10 · Этап-2 · 27.09.2026

## 1. Назначение и границы
Заимствование инженерных механик опенсорс-платформы TencentCloud/Octop (MIT,
github.com/TencentCloud/Octop, анализ 27.09.2026) для вех Этап-2 (M10–M12) и
смежных контуров. Берём **паттерны и решения, не платформу**: код Octop не
становится зависимостью, LangGraph/WS/десктоп не внедряются.

Принцип-наследник ROADMAP: новые блоки встраиваются в существующий порядок
вех (M10 → M11 → M12), путь B не нарушается — мультиагентность (О5) до
прохождения порога B→A оформляется только контрактом, без кода в UI.

Non-goals:
- Не переписывать стек (Alpine без сборки, BFF FastAPI, PostgreSQL, Qdrant — как решено).
- Не вводить WebSocket-стрим, персона/MBTI, маркет экспертов, китайские IM-каналы.
- Не подключать код Octop как библиотеку; референс — архитектура и фиксы их changelog.

## 3. Блоки интеграции

### О1 · RAG-контур M11: ingestion + цитирование · зависит от M10 · объём L
Расширяет CONTRACTS §9 (сущности §9.1–9.2 не меняются, добавляются механики).

Требования:
1. **Конвейер документа** — статусы `uploaded → parsed → chunked → indexed →
   ready | failed(reason)`; пайплайн идемпотентен (повторный запуск по doc_id
   не плодит дубли чанков в Qdrant — очистка по doc_id перед переиндексацией).
2. **Форматы**: pdf, docx, xlsx/csv, md/txt. PDF без текстового слоя →
   OCR (rapidocr, extra-зависимость); OCR-отказ («нет изображения» и т.п.)
   → `failed(no_text)`, НЕ «ready» с пустым корпусом (фикс-паттерн Octop).
3. **Кодировки**: UTF-8 → при провале cp1251 (ру-аналог фолбэка GB18030 у
   Octop); недекодируемое — `failed(encoding)`.
4. **Чанкинг**: CHUNK_SIZE=1000 симв., CHUNK_OVERLAP=15% (конфиг BFF);
   чанк хранит doc_id, kb_id, порядковый номер, quote-диапазон.
5. **Эмбеддинг**: провайдер, уже подключённый к BFF (параметр
   EMBED_PROVIDER); локальный fastembed — опция, вне MVP.
6. **Цитирование** (ужесточение §9.2): ответ orchChat на knowledge-запрос
   обязан содержать citations[] = {doc_id, title, chunk_id, quote};
   ответ без валидных citations помечается `unverified` и деградирует до
   обычного чата (без значка «знание» в UI). Источник каждого утверждения
   кликабелен: doc → chunk → подсветка quote.
7. **Версия корпуса** (принцип M9): corpus_version инкрементируется при
   каждом изменении корпуса; orchChat фиксирует corpus_version в runlog.

DoD О1: 1) на тестовом корпусе (pdf с текстом, pdf-скан, docx cp1251, csv,
битый файл) все 5 исходов конвейера воспроизводятся; 2) knowledge-запрос без
источников в ретриве не выдаёт значок «знание»; 3) повторная индексация не
создаёт дублей; 4) corpus_version отражается в runlog.

### О2 · Коннекторный слой M10 · объём M
Расширяет CONTRACTS §8 (таблица sources и эндпоинты §8.2 не меняются).

Требования:
1. **Единый интерфейс коннектора**: `kind (rss|api|web|kb)`, `auth:
   none|apikey|oauth` (у одного коннектора — оба варианта, паттерн 企查查),
   `fetch(params) → [observation]`, `normalize() → insights/ux_signals`.
   Коннектор — модуль `backend/connectors/<name>.py`, регистрируется в
   реестре; новый источник = новый модуль + строка в `sources`.
2. **Стартовый набор**: arXiv (api, auth:none), КиберЛенинка (web/search,
   auth:none), открытые ресурсы (rss, auth:none). OpenAlex-коннектор Octop —
   референс кода для научных API.
3. **Наблюдения коннектора** всегда несут source_id → в UX-контур попадают
   только со статусом источника `verified` (жизненный цикл §8.1);
   `revoked`/`proposed` источники не поставляют данные.
4. OAuth (если у источника нет API-Key): код-обмен с **PKCE S256**;
   callback — только по явному списку redirect-uri (фикс-паттерн Octop
   «OAuth 回调安全加固»).

DoD О2: 1) arXiv-коннектор возвращает нормализованные наблюдения с source_id;
2) источник в статусе proposed не отдаёт данные в мониторинг; 3) добавление
нового rss-источника — без правок кода (только строка в sources).

### О3 · Механика агентных вопросов M12 · зависит от О1, О2 · объём S
Расширяет CONTRACTS §10 (таблица agent_questions уже содержит статусы
asked|deferred|answered|expired — добавляется поведение).

Требования (паттерны фикс-лога Octop HITL):
1. **TTL**: AGENT_QUESTION_TTL=72ч (конфиг); фоновая джоба переводит
   asked→expired; вопрос с истёкшим TTL НЕ считается «принятым» и не
   попадает в обучающие сигналы Q-метрики (M9).
2. **Идемпотентность показа**: фронт показывает каждый вопрос один раз —
   дедупликация по question.id при рестарте/переключении сессии; повторное
   внедрение в чат запрещено.
3. **Гашение при новом раунде**: старт нового раунда ПЕТРУШКИ погашает
   оставшиеся asked-вопросы предыдущего раунда (→ expired), чтобы в чате
   не висели «хвосты».
4. **Отложенный ответ из лога** (§10.2 сохраняется): answer из лога
   валидирует, что вопрос ещё не expired.

DoD О3: 1) после рестарта страницы вопрос не дублируется; 2) вопрос старше
TTL в обучающий сигнал не попадает; 3) новый раунд гасит старые asked.

### О4 · Дисциплина таймзон расписаний · объём S · вне очереди вех
Требования (фикс-паттерн Octop «date:/cron: → default_timezone, не зона хоста»):
1. DEFAULT_TZ=Europe/Moscow — единый конфиг BFF; все расписания (aiDigest,
   expiry-джоба О3, очистка runlog) указывают TZ явно.
2. Время в API и логах — ISO 8601 с offset; «голые» ISO-времена без offset
   трактуются как DEFAULT_TZ, а не как зона хоста.
3. Метeo-таймеры (systemd) и cron BFF сверены на один TZ-слой (проверка
   на расхождение МСК/UTC у хоста).

DoD О4: перевод часов сервера в другую зону не сдвигает время aiDigest.

### О5 · RFC «фамильяр ↔ ядро» (подготовка порога B→A) · объём S (документ)
Только документ-контракт, код — после прохождения порога B→A (принцип
«не возвращаться к A первым шагом»).

Референс — docs Octop: agent-delegation, agent-call-agent, agent-interop-mailbox,
expert-teams (координатор перезаписывает задания, артефакты команды, трасса
инструментов). В RFC зафиксировать:
1. Сущность mailbox: message {id, from_agent, to_agent|'CORE', kind,
   payload, status, created_at} — аудит совместим с actor_name (M6).
2. Протоколы: делегирование задания, запрос к другому фамильяру, возврат
   артефакта; каждый переход — запись в аудит.
3. Критерии готовности системы к A: какие Q-метрики (M9) и объёмы
   открывают реализацию.

DoD О5: RFC согласован заказчиком, сохранён в docs/, ссылка из ROADMAP.

### О6 · Telegram-канал ПЕТРУШКИ · зависит от О3 · объём M
Исходящий/входящий чат-канал ПЕТРУШКИ по образцу octop-gateway
(ChannelManager, привязка канала к агенту и пользователю).
ВАЖНО: не путать с SMM-мониторингом каналов (Блок 1, входящие наблюдения) —
это отдельный контур, его не трогаем.

Требования:
1. Таблица `channel_bindings` {user_id, channel='telegram', chat_id,
   verified_at, notify_mask (digest|questions|insights)}; привязка —
   командой в боте, подтверждение пользователя.
2. `POST /v1/telegram/webhook` — secret-token в заголовке; входящие тексты
   только от привязанных chat_id → orchChat от имени пользователя;
   непривязанные — игнор с журмированием.
3. Исходящие push: aiDigest, agent_questions (со ссылкой на ответ в логе),
   accepted-insights — строго по notify_mask пользователя (opt-in).
4. Ключ сессии ПЕТРУШКИ: `<user_id>:telegram:<chat_id>` — отдельная
   session-нить, не пересекается с веб-чатом (паттерн ключей Octop).

DoD О6: 1) digest доходит только пользователям с включённым notify_mask;
2) текст от постороннего chat_id не попадает в orchChat; 3) вопрос из
Telegram отвечает в тот же контур (лог agent_questions, ответ и из веба,
и из TG — единый).

### О7 · Инженерная гигиена · объём S · вне очереди вех
1. **AGENTS.md в корне репо** (паттерн Octop: границы модулей, жёсткие
   запреты, отличие от человеческой документации): карта модулей backend/*,
   запреты (не править js/mock.objects.js в apiMode; esc() обязателен во
   всех innerHTML; прод — только после подтверждения), связка с существующими
   промпт-файлами (COMET_PROMPT, OPENCLAW_PROMPT, HANDOVER).
2. **CodeQL workflow** в CI (адаптация codeql.yml Octop, MIT).
3. **argon2-cffi** вместо bcrypt (миграция прозрачно при следующем логине:
   проверка обоих хешей, перехэш при успехе).
4. PKCE для OAuth-коннекторов — в О2 п.4.

DoD О7: AGENTS.md принято; CodeQL зелёный; вход со старым bcrypt-хешем
прозрачно перехэшируется.

## 5. Порядок исполнения
1. О7 + О4 — сразу (низкая цена, не ждут вех).
2. О2 — в веху M10. 3. О1 — в веху M11. 4. О3 — в веху M12.
5. О5 (RFC) — параллельно, код после порога B→A. 6. О6 — после M12.
Каждый блок: анализ → согласование → правки в исходники (после подтверждения
заказчика) → верификация по DoD → фиксация. Прод-код — только после явного
подтверждения заказчика.

## 6. Риски
- Qdrant/OCR — новые инфраструктурные зависимости на сервере BFF: согласовать
  установку до старта О1.
- Telegram-бот: исходящие лимиты API; приaudit-паузе digest не теряется
  (повтор в следующем цикле).
- Цитирование может деградировать полноту ответов orchChat — прогнать
  тестовый корпус до перевода в прод.
- RFC О5 провоцирует «ранний уход в A» — контроль: код фамильяров не пишем
  до порога B→A по Q-метрикам M9.
