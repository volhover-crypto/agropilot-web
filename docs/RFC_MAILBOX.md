# RFC: «фамильяр ↔ ядро» — межагентное взаимодействие (О5, подготовка порога B→A)

Статус: **черновик, на согласовании заказчиком** (DoD О5). Код по этому RFC не
пишется до прохождения порога B→A (принцип ROADMAP «не возвращаться к A
первым шагом»; риск «раннего ухода в A» из ТЗ_ИНТЕГРАЦИЯ_OCTOP §6).

Референсы: docs Octop — agent-delegation, agent-call-agent,
agent-interop-mailbox, expert-teams (координатор перезаписывает задания,
артефакты команды, трасса инструментов). Берём паттерны, не код.

## 1. Назначение
Сейчас система — путь B: один модератор ПЕТРУШКА + объектный стол. Когда
объём и качество работы в режимах CONFIRM/AUTO стабильно высоки (порог §4),
появляется основание выделить отдельного «фамильяра» (персонального агента
направления). Фамильярам нужен протокол обмена без прямых вызовов —
через почтовый ящик с аудитом.

## 2. Сущность mailbox
```sql
-- черновик схемы (не миграция! реализация после порога B→A)
agent_mailbox (
  id          uuid PRIMARY KEY,
  ts          timestamptz NOT NULL DEFAULT now(),
  from_agent  varchar(32) NOT NULL,     -- ключ агента из agent_cards (028) | 'CORE'
  to_agent    varchar(32) NOT NULL,     -- ключ агента | 'CORE' (ядро-оркестратор)
  kind        varchar(16) NOT NULL,     -- task | request | artifact | answer | escalation
  payload     jsonb NOT NULL,
  status      varchar(16) NOT NULL DEFAULT 'new',  -- new|delivered|done|failed
  round_id    varchar(64)               -- раунд ПЕТРУШКИ (см. CONTRACTS §40)
)
```
Аудит: каждый переход сообщения (new→delivered→done/failed, перезапись
задания координатором) — запись в существующие `run_logs` (миграция 032)
с `agent_key` отправителя/получателя и `meta.message_id`; для действий в
сделках — actor_name по M6. Отдельной таблицы аудита не вводим.

## 3. Протоколы
1. **Делегирование задания** (CORE → фамильяр): kind=task, payload=
   {goal, context_refs[], deadline, constraints}. Координатор вправе
   перезаписать задание (новое сообщение, старое → failed/замещено) —
   паттерн expert-teams.
2. **Запрос к другому фамильяру** (фамильяр → фамильяр): kind=request,
   ответ kind=answer обязателен или escalation ядру по таймауту.
3. **Возврат артефакта** (фамильяр → CORE): kind=artifact, payload=
   {artifact_ref (таблица artifacts), summary, quality_self}.
   Артефакт попадает в объектный стол, решение о принятии — за человеком
   (CONFIRM) или по правилу (AUTO), как в текущем конвейере.

## 4. Q-метрики и порог B→A (формализация — первое упоминание в проекте)
Q-метрики M9 в репо не определены; предлагаемое определение (согласовать):
на скользящем окне 30 дней по каждому навыку (skills, versions):
- **точность** precision = accepted / (accepted + rejected) — по сигналам
  принятия/отклонения его продуктов (insights, рекомендации, ответы);
- **ответность** responsiveness = answered / (answered + expired) — по
  agent_questions (§40: expired-вопросы в числитель не попадают);
- **объём** volume = число сигналов (принятий+отклонений+ответов) за окно.

**Порог выделения фамильяра (B→A):** precision ≥ 0.7 И volume ≥ 30
на двух подряд окнах по одному направлению. Ниже порога — остаётся один
модератор ПЕТРУШКА (фамильяры «виртуальные»: контракты есть, кода нет).

## 5. Что НЕ входит в RFC
LangGraph/WS/десктоп, персон/MBTI, IM-мосты (кроме уже спланированного
Telegram О6), автогенерация новых агентов без порога.

## 6. Открытые вопросы к согласованию
1. Формулы Q-метрик §4 (пороги 0.7 / 30 / два окна).
2. Допустимость перезаписи задания координатором без подтверждения человека
   в режиме CONFIRM.
3. Таймаут ответа фамильяра на request (предложение: 24 ч).
